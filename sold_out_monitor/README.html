Sold Out Monitor

這是一個給 Ticket Plus 活動頁使用的「售完狀態監控器」。它會開啟 Chrome 等前端渲染完成， 掃描活動頁 立即購買 區塊底下的所有場次；只要某個場次不再顯示 銷售一空，就發送 webhook，並可同步通知 Chrome extension 開始執行。

主要入口：Python / exe 保留舊版：legacy_node 活動切換：改 ticketplus_url 需要前端渲染：Playwright + Chrome

這份資料夾在專案裡的位置

目前放在 Chrome extension 專案底下： C:\Users\Lu_white\Documents\chrome_extension\ticket_plus_bot\sold_out_monitor

給使用者看的重點

正常使用時只需要改 monitor_config.json，然後跑 start-monitor.bat。

給下一個 Codex 的重點

不要用 raw HTML 判斷 Ticket Plus 場次。這個網站的關鍵字是前端渲染後才出現在 DOM 裡。

檔案導覽

檔案 用途
monitor.py 主要 Python 原始碼。負責開 Chrome、讀取活動頁、解析場次、發 webhook、觸發 extension。
dist\sold_out_monitor.exe 已打包好的 Windows 執行檔。不想安裝 Python 時可以直接用它。
monitor_config.example.json 設定範例。第一次跑 start-monitor.bat 時，若沒有 monitor_config.json 會自動複製一份。
start-monitor.bat 最直覺的啟動入口。優先跑 exe，沒有 exe 才 fallback 到 Python。
test-notify.bat 測試 webhook / extension trigger 是否能送出。
build-exe.bat 重新打包 exe 用。會安裝 requirements 並呼叫 PyInstaller。
requirements.txt Python 依賴，目前包含 playwright 與 pyinstaller。
legacy_node\ 原本 Node.js 監控器的備份。沒有複製 node_modules、logs、runtime state。

監控流程

這份監控器的核心邏輯是「等前端渲染，再讀畫面文字」，流程如下：

用 Playwright 啟動 Chrome，開啟 ticketplus_url。
等待頁面前端渲染，直到 DOM 裡出現 立即購買。
讀取 document.body.innerText，不是抓 raw HTML。
找到真正的 立即購買 場次區塊。
解析所有場次名稱、日期、時間、地點、售票狀態。
如果某場次不含 銷售一空，視為有票或可進入訊號。
發送 webhook，並依設定 POST/GET 到 extension trigger server。

立即購買如何避免誤判

Ticket Plus 頁面上方導覽列也會有一個 立即購買。監控器不會看到第一個就相信它， 而是只接受後面很近的位置出現場次欄位的 立即購買。

目前判斷條件：

  • 逐行掃描所有文字。
  • 找到文字等於 立即購買 的行。
  • 檢查它後面 12 行內是否有 場次名稱 和 售票狀態。
  • 或檢查是否有 日期 / 時間 這種舊格式欄位。
  • 如果後面只是 活動介紹、注意事項、購買提醒，就視為導覽列並跳過。
導覽列立即購買：立即購買 -> 活動介紹 -> 注意事項 -> 購買提醒
結果：跳過

真正場次區塊：立即購買 -> 場次名稱 -> 場次日期 -> 場次時間 -> 場次地點 -> 售票狀態
結果：開始解析場次

有票訊號如何判斷

目前規則很直接：場次 evidence 裡包含 銷售一空 就視為售完；不包含 銷售一空 就視為可通知。

注意：尚未開賣、立即購買、熱賣中 都會被歸類為「不是銷售一空」。 這是刻意做成廣義訊號。如果未來只想通知 立即購買 或 熱賣中，要改成白名單判斷。

設定說明

設定 說明
ticketplus_url 要監控的 Ticket Plus 活動頁。換活動通常只改這個。
webhook_url 通知目的地，目前預設是 ntfy topic。
webhook_format ntfy 或 json。ntfy 會用文字訊息，json 會送完整 payload。
extension_trigger_enabled 是否同步通知 Chrome extension 的 local trigger server。
extension_trigger_url 預設 http://127.0.0.1:16888/trigger，要搭配 extension 那邊的 trigger_server.py。
extension_trigger_method POST 或 GET。POST 會送 JSON payload；GET 會自動加 ?fire=1。
headless false 會看得到 Chrome 視窗；true 會背景執行。
browser_channel 預設 chrome，代表使用本機已安裝的 Chrome。
poll_min_ms / poll_max_ms 每輪監控間隔會在這兩個毫秒數之間隨機。
alert_repeat_count 偵測到可通知場次時 webhook 重複發送次數。
alert_repeat_interval_ms 重複通知之間的間隔。
sold_out_text 判斷售完用的文字，預設 銷售一空。 
{
  "ticketplus_url": "https://ticketplus.com.tw/activity/...",
  "webhook_url": "https://ntfy.sh/your-topic",
  "extension_trigger_enabled": true,
  "extension_trigger_url": "http://127.0.0.1:16888/trigger",
  "extension_trigger_method": "POST",
  "headless": false
}

和 Chrome Extension 的關係

這個 monitor 本身只負責「看到不是銷售一空」並發出訊號。真正開始搶票的動作仍在 Chrome extension 那邊。兩邊用 local trigger server 串接。

角色 責任
sold_out_monitor 監控活動頁所有場次，發 webhook，通知 127.0.0.1:16888/trigger。
trigger_server.py 接收外部 POST/GET 訊號，供 extension 的「外部觸發」測試或啟動流程讀取。
Chrome extension 收到 trigger 後，在 Ticket Plus 頁面執行原本的自動流程。

排錯筆記

  • 如果完全抓不到場次，先確認是不是用 raw HTML 在看；正確方式一定要前端渲染後讀 DOM。
  • 如果 exe 開不起 Chrome，確認本機有安裝 Chrome，或調整 browser_channel。
  • 如果 extension 沒反應，先確認 trigger_server.py 有跑，且網址是 http://127.0.0.1:16888/trigger。
  • 如果不想真的通知，把 webhook_url 清空、extension_trigger_enabled 設成 false，再用 --once 看輸出。
  • runtime 產生的 .ticketplus-monitor-state.json 是狀態檔，不應該 commit。

給下一個 Codex 的接手提醒

修改這個專案時，請先從真實活動頁跑一次 --once 驗證。不要只看單元測試或 raw HTML， 因為 Ticket Plus 的可售狀態是 client-rendered。上次驗證用的活動頁是 Vaundy，exe 能抓到 2026-10-31 與 2026-11-01 兩個場次，狀態皆為 銷售一空。

如果要改「有票」判斷，優先改 monitor.py 裡的狀態規則，並同步更新這份 README。 如果要改部署方式，確認 start-monitor.bat、build-exe.bat、README.md 和這份 HTML 都一致。
